Astro Survey Atlas / Scan engine

Scan your data sources.
Build a searchable sky index.

Warehouse is a scanning tool for astronomical data. Point it at a local directory, an S3-compatible bucket, or OSS storage. It inventories every file it finds, extracts each file's sky coverage from supported metadata, and writes the current results into Elasticsearch ast_* indices, retaining evidence for every scan. It never reads or copies scientific arrays.

Once a scan lands in the index, the sky-position questions come from your application: which files cover this region, where do they live, and why did they match. Assets asks this in production; your code can query the same indices.

What Warehouse does with your data

Inventory the files

One scan walks one source and records every discovered file as a FileAsset with its canonical URI, name, size, and timestamps.

Extract sky coverage from metadata

One extraction mode per scan reads WCS headers, catalog RA/Dec columns, or explicit HEALPix cells. Every result carries its precision: exact, estimated, or entrypoint-only.

Publish current state to Elasticsearch

Each scan refreshes one CoverageLayer in the ast_* indices. Only ACTIVE layers are queryable; failed scans stay visible with errors and evidence instead of serving stale coverage.

A CoverageLayer groups one survey, release, and product; one scan covers one source, one layer, and one extraction mode. To answer "which files cover this part of the sky", query the indices a scan produced: Assets reads them in production, and the diagnostic Query API lets you try the same lookup.

02 / Extraction

Choose how to read your sky coverage

fits-wcs

Image and cube footprints

Reads supported WCS headers and rasterizes at the required outputOrder. Sampled coverage is estimated; there is no silent center-point fallback.

fits-header-position

Header position evidence

Maps an explicit FITS header position at the required outputOrder. Precision is entrypoint-only, not an instrument footprint.

catalog-radec

Catalog occupancy

Reads configured RA and Dec columns in ICRS degrees and maps them to NESTED cells at outputOrder. Coverage describes file occupancy, not a per-row object index.

catalog-healpix

Explicit source cells

Requires a pixel column and exactly one fixed source order or order column. Preserves explicit NESTED order/ipix; an absent source order is never assumed to be 8.

What if one folder contains multiple kinds of files?

Astronomical data is usually separated by product type into directories or object prefixes. Create a ScanPlan for one directory or prefix and choose the extraction mode that matches that batch of files. You can filter by suffixes and exclude README/checksum files or other auxiliary inputs. Only when one path mixes different spatial-recording methods do you need to split into multiple scan plans.

Local, S3-compatible, and OSS sources

The local connector accepts a directory or single file. S3-compatible and OSS endpoints use the AWS SDK adapter, with canonical s3://bucket/key or oss://bucket/key identities. Supply a signing region when required. Credential references point to environment variables or mounted files; never put credential values in a plan.

Databases (JDBC) are planned, not supported yet. The current ScanPlan accepts local, S3-compatible, and OSS sources only. Until a JDBC connector lands, scan catalog databases with Workspace, whose connectors include JDBC and write to its own index.

Metadata only. FITS extraction reads headers, and catalogs expose configured spatial columns. Warehouse never reads or copies scientific image, spectrum, or cube arrays. Unsupported formats remain discovered FileAssets with evidence and no invented coverage.

Declare modality explicitly:

  • image
  • spectrum
  • cube
  • catalog
  • timeseries
  • visibility
  • event
  • other

03 / Submission

Run a scan, then check the result

Connecting to an existing deployment? Ask its operator for your request namespace, source and evidence volumes, scanner image, and Elasticsearch settings. Submit scans through Kubernetes ScanRequest. The read-only Query API is used later to look up files.

Start with a bounded catalog and a complete ScanPlan v2. The example below expects CSV or TSV files with ra and dec columns under /data.

1. Inspect a local catalog

This is a complete scan-plan.json. Adapt the source and evidence paths to your machine. The sink remains declared even when --memory bypasses Elasticsearch.

scan-plan.json / ScanPlan v2
{
  "version": 2,
  "scanRunId": "local-catalog-example",
  "layer": {
    "layerId": "local-catalog-example",
    "surveyId": "example",
    "releaseId": "local",
    "productId": "catalog",
    "modality": "catalog",
    "coverageRole": "occupancy"
  },
  "source": {
    "connector": {"type": "local"},
    "location": {"rootPath": "/data"}
  },
  "filters": {"includeSuffixes": [".csv", ".tsv"]},
  "extraction": {
    "mode": "catalog-radec",
    "outputOrder": 8,
    "catalog": {"raColumn": "ra", "decColumn": "dec"}
  },
  "sink": {
    "connector": {
      "type": "elasticsearch",
      "endpoint": "http://localhost:9200",
      "credentialRef": {}
    }
  },
  "evidence": {
    "outputPath": "/var/lib/atlas-evidence/local-catalog-example"
  }
}
Local CLI / from the repository root
mvn -B package
java -jar scanner-cli/target/scanner-cli-0.1.0-SNAPSHOT-runner.jar \
  --plan /path/to/scan-plan.json --memory

Memory diagnostics do not persist searchable state. Evidence is optional only with --memory; if declared, use a writable output path. To persist, omit --memory, configure the new Warehouse Elasticsearch endpoint and credential references, provision the strict indices, and retain evidence. Scanner startup does not create or recreate indices.

2. Submit a namespaced ScanRequest

For a deployed Warehouse, submit the plan as a ScanRequest using the example below. Ask your operator to provide an evidence PVC and a Bound source PVC labelled atlas.zhejianglab.org/scanner-source=true in atlas-warehouse. The source claim's catalogs subdirectory is mounted read-only at /data.

scanrequest-local.example.yaml
apiVersion: atlas.zhejianglab.org/v1alpha1
kind: ScanRequest
metadata:
  name: local-catalog-example
  namespace: atlas-warehouse
spec:
  scanner:
    image: ghcr.io/astro-survey-atlas/astro-atlas-scanner:0.1.0
    backoffLimit: 0
    activeDeadlineSeconds: 3600
    evidence:
      claimName: atlas-evidence
      mountPath: /var/lib/atlas-evidence
    sourceVolume:
      claimName: atlas-source-catalogs
      mountPath: /data
      subPath: catalogs
  plan:
    version: 2
    scanRunId: local-catalog-example
    layer:
      layerId: local-catalog-example
      surveyId: example
      releaseId: local
      productId: catalog
      modality: catalog
      coverageRole: occupancy
    source:
      connector:
        type: local
      location:
        rootPath: /data
    filters:
      includeSuffixes: [.csv, .tsv]
    extraction:
      mode: catalog-radec
      outputOrder: 8
      catalog:
        raColumn: ra
        decColumn: dec
    sink:
      connector:
        type: elasticsearch
        endpoint: http://atlas-warehouse-elasticsearch:9200
        credentialRef: {}
    evidence:
      outputPath: /var/lib/atlas-evidence/local-catalog-example

The endpoint and image are example deployment settings, not universal defaults. This request assumes a sink without authentication; authenticated deployments must add namespace-local Secret bindings and plan credential references. Source paths must stay inside the declared source mount, and evidence paths inside the evidence mount. Host paths and cross-namespace claims are not supported.

Upstream examples: complete local request, OSS request with Secret references, and Helm installation.

3. Observe execution and evidence

Submit and monitor / configured cluster required
kubectl apply -f deploy/kubernetes/scanrequest-local.example.yaml
kubectl -n atlas-warehouse get scanrequest local-catalog-example -w

# In another terminal, inspect status and the reported Job name.
kubectl -n atlas-warehouse get scanrequest local-catalog-example -o yaml
JOB_NAME=$(kubectl -n atlas-warehouse get scanrequest local-catalog-example \
  -o jsonpath='{.status.jobName}')
kubectl -n atlas-warehouse logs "job/${JOB_NAME}" --follow

Wait for a Job name before requesting logs. Request phases are INVALID, WAITING, SUBMITTED, RUNNING, SUCCEEDED, and FAILED. The summary reports counts, available orders, source snapshot hash, errors, and evidence path. Detailed inventory, normalized scan, provenance, and errors stay on the evidence volume, not in the browser's initial request.

Submission is asynchronous: accepting the request does not mean the scan has finished. Follow its status until SUCCEEDED, FAILED, or INVALID. If it remains WAITING, inspect the status message. Your namespace must be enabled by the deployment operator; all volume and Secret references belong in that same namespace.

04 / Reverse lookup

Ask for cells. Receive file candidates.

Already have an indexed layer? Send its ID and the sky cells you want to search to the diagnostic Query API below. Ask your operator for its address if it is enabled. Applications can also read Warehouse Elasticsearch directly; this is how Assets performs production lookups.

GET /v2/files/healpix
# Point this at your separately running diagnostic Query API.
QUERY_API=http://localhost:8080
curl --fail-with-body --get "$QUERY_API/v2/files/healpix" \
  --data-urlencode 'layers=local-catalog-example' \
  --data-urlencode 'order=8' \
  --data-urlencode 'pixels=123' \
  --data-urlencode 'limit=100'

Replace pixel 123 with a cell from your scan evidence. Supply comma-separated layers and pixels, and one explicit order. Every requested layer must be ACTIVE and support that order. Results contain unique files and their matchingCoverage; they are cell-intersection candidates, not exact geometric overlap claims.

The default limit is 100, maximum 1000. A response or edge limit sets truncated=true. When nextCursor is non-null, pass it as the opaque cursor with the same normalized layers, order, and pixels. Do not treat truncation as a precision value or assume every truncated response has another page.

Read the response in three steps

  1. Find the files. Each item contains fileId, sourceUri, fileName, and fileType. Use sourceUri to locate the original file; Warehouse does not serve its contents.
  2. Check why they matched. matchingCoverage lists the matching layerId, order, pixel, method, role, and precision. One file can have several matching cells.
  3. Check whether there is more. truncated tells you the result was limited. Continue only when nextCursor is non-null, keeping the same layers, order, and pixels.

An empty items list means no candidate files matched this query on available layers. A layer-state error means the layer cannot currently be queried. Handle those as different outcomes in your application.

05 / Storage contract

Where to find layers, files, and coverage

Reading Elasticsearch directly? Start with the layer to check its state and available orders, find matching coverage cells, then resolve their file IDs. The three indices below hold the current scan results.

  1. Read ast_layer_index_v1 for your layer_id. Query only ACTIVE layers, and choose an order listed in available_orders.
  2. Search ast_coverage_index_v1 by layer_id, healpix_order, and healpix_cell. Keep the precision and method alongside each match.
  3. Deduplicate source_file_id values and resolve them as file_id in ast_file_index_v1 to retrieve file metadata and source_uri.

For production reads, follow the index contract linked below, including its state checks and result limits. The explorer shows field names and sample documents; it does not connect to your Elasticsearch.

CoverageLayer

ast_layer_index_v1 holds survey/release/product identity, modality, role, entrypoint, state, lease, snapshot hash, available orders, counts, and errors. Document ID: layer_id.

FileAsset

ast_file_index_v1 holds canonical URI, name/type, parent URI, size, and timestamps. Document ID: SHA-256 of the canonical source URI. No raw data, modality, or layer-owned coverage list.

SpatialCoverage

ast_coverage_index_v1 associates a layer and file with an explicit cell, method, role, modality, and precision. Identity is deterministic over layer, file, order, cell, and role.

The offline explorer displays mapping fields and illustrative documents. Read the canonical templates for the authoritative field definitions.

Canonical sources: strict Elasticsearch templates and index identity, write, and read contract.

06 / Understanding results

How much does a match tell you?

Every coverage result is stored as HEALPix cells: sky pixels identified by ICRS, an explicit NESTED order, and an ipix. The precision label describes how those cells were obtained; response truncation is separate.

Three precision levels describe the evidence behind the stored HEALPix pixels:

exact

The input identifies the represented HEALPix pixels directly, or a catalog coordinate is deterministically assigned to an occupancy pixel. This is exact cell evidence, not an exact polygon boundary.

estimated

The pixels are sampled or inferred from metadata, such as WCS rasterization. They are useful coverage candidates, but they are not an exact footprint geometry.

entrypoint-only

Only a product location or explicit position is known. This is not a file footprint and does not create synthetic HEALPix cells or a file-level coverage edge.

Finer source pixels may be coarsened to a lower order. A coarse pixel is never expanded into invented finer pixels. This rule is independent from response truncation.

Check availability before showing results

UPDATING

A scan is refreshing this layer. Show it as temporarily unavailable and try again later; this state does not mean the region has no data.

ACTIVE

Only verified successful current state is searchable. A successful empty scan is ACTIVE with zero coverage, a valid empty result.

FAILED

The scan failed, so this layer is unavailable. Check the error summary and scan evidence before submitting a new scan. Partial results and previous coverage are not returned.

Failure is terminal for an execution. The first extraction error, including a malformed catalog row, stops the scan and is retained as evidence. Later input is not enumerated. Jobs use backoffLimit=0; diagnose and submit a new request/execution identity to retry. Only bounded transport retries remain. Suffix filtering, blank lines, and comments are not failures.

Need to investigate a scan? Start with its summary for counts, errors, and the evidence path. Ask your operator for access to the detailed inventory and extraction records at that path. The source snapshot hash identifies the scanned inventory, not the contents of each scientific file.
